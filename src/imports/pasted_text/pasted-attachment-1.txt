Here's a comprehensive checklist for vibe coding web and mobile apps, organized by the four pillars you mentioned:

## 1. Architecture & Organization

**Project structure**
- [ ] Consistent folder structure (feature-based or layer-based — pick one, don't mix)
- [ ] Clear separation: UI components / business logic / data layer / utilities
- [ ] Config, constants, and environment variables isolated from logic
- [ ] One component/module = one responsibility (if a file does 5 things, split it)

**Naming & readability**
- [ ] Descriptive, consistent naming conventions (camelCase/PascalCase/kebab-case applied predictably)
- [ ] No abbreviations that only make sense in the moment (`btn2`, `tempFix`, `dataX`)
- [ ] File names match their default export/component name

**Modularity**
- [ ] Reusable components extracted (buttons, cards, inputs) instead of copy-pasted
- [ ] Business logic separated from presentation (hooks/composables/services, not embedded in JSX/views)
- [ ] No hardcoded values — use design tokens, constants, or config files
- [ ] Shared logic (validation, formatting, API calls) centralized, not duplicated per screen

**Documentation & comments**
- [ ] README explains setup, architecture decisions, and folder structure
- [ ] Complex logic has "why" comments, not "what" comments
- [ ] Component props/function signatures documented (JSDoc/TSDoc or type annotations)
- [ ] AI-generated sections flagged/reviewed — don't let vibe-coded blocks silently accumulate without understanding what they do

## 2. Vibe-Coding-Specific Hygiene

- [ ] Every AI-generated chunk gets read and understood before moving on — never paste-and-pray
- [ ] Version control commits are small and frequent, so you can bisect when something breaks
- [ ] No duplicate logic introduced because you forgot an existing utility already does it (search before generating)
- [ ] Dependencies are checked before adding — don't let AI pull in a new library for something one utility function could solve
- [ ] Linting + formatting (ESLint/Prettier or equivalent) enforced automatically, not manually reviewed
- [ ] Type safety enabled (TypeScript, PropTypes, or equivalent) — catches AI hallucinated props/fields early
- [ ] Tests exist for critical paths (auth, payments, data mutations) even if coverage isn't 100%
- [ ] Secrets/API keys never hardcoded — checked explicitly since AI tends to inline them for convenience

## 3. Performance

**Web**
- [ ] Code splitting / lazy loading for routes and heavy components
- [ ] Images optimized (WebP/AVIF, responsive `srcset`, lazy loading)
- [ ] Bundle size monitored (tree-shaking working, no accidental full-library imports like `import _ from 'lodash'`)
- [ ] Debounce/throttle on expensive operations (search inputs, scroll listeners, resize handlers)
- [ ] Memoization used deliberately (`useMemo`, `useCallback`, `React.memo`) — not sprinkled everywhere without profiling
- [ ] No unnecessary re-renders (check with DevTools profiler)
- [ ] Critical CSS/above-the-fold content prioritized
- [ ] Caching strategy for API calls (stale-while-revalidate, proper cache headers)

**Mobile**
- [ ] List rendering virtualized for long lists (FlatList/RecyclerView equivalents, not mapping huge arrays directly)
- [ ] Images sized appropriately for device density, not loaded at full resolution everywhere
- [ ] Animations run on native thread/GPU where possible, avoid janky JS-thread animations
- [ ] Cold start time measured and minimized (lazy-load non-critical modules)
- [ ] Offline handling / graceful degradation for poor connectivity
- [ ] Battery/network-conscious background tasks (avoid polling when push/websockets would do)

**General**
- [ ] Database queries/API calls checked for N+1 problems
- [ ] Pagination/infinite scroll instead of loading everything at once
- [ ] Performance budgets defined (load time, bundle size) and checked in CI, not just eyeballed

## 4. Accessibility (WCAG-aligned)

**Structure**
- [ ] Semantic HTML used correctly (`button` not `div onClick`, proper heading hierarchy `h1→h2→h3`)
- [ ] Landmarks present (`nav`, `main`, `header`, `footer`) for screen reader navigation
- [ ] Forms have associated `label`s, not just placeholder text

**Interaction**
- [ ] Full keyboard navigability (tab order logical, no keyboard traps)
- [ ] Visible focus states on all interactive elements
- [ ] Touch targets ≥44x44px on mobile (Apple/Android guidelines)
- [ ] Gestures have accessible alternatives (swipe-to-delete also has a button option)

**Perception**
- [ ] Color contrast meets at least AA (4.5:1 text, 3:1 large text/UI components)
- [ ] Color never the sole indicator of meaning (error states also use icon/text, not just red)
- [ ] Alt text on meaningful images; decorative images marked `alt=""` or `aria-hidden`
- [ ] Captions/transcripts for video and audio content

**Assistive tech**
- [ ] ARIA used only when semantic HTML can't do the job (don't over-ARIA)
- [ ] Dynamic content changes announced via `aria-live` where relevant (form errors, toasts, loading states)
- [ ] Screen reader tested at least once per major flow (VoiceOver/TalkBack, not just automated tools)
- [ ] Text resizable up to 200% without breaking layout
- [ ] Reduced motion respected (`prefers-reduced-motion`) for animations

## 5. UX Best Practices

**Feedback & states**
- [ ] Loading, empty, error, and success states designed for every screen — not just the happy path
- [ ] Errors are actionable (tell the user what to do, not just "something went wrong")
- [ ] Optimistic UI or clear loading indicators for any action >300ms
- [ ] Confirmation for destructive actions (delete, logout, irreversible submits)

**Consistency**
- [ ] Design system/component library enforced — spacing, typography, and colors pulled from tokens, not one-off values
- [ ] Interaction patterns consistent across the app (same gesture/button style means the same thing everywhere)
- [ ] Copy tone and terminology consistent (don't say "Delete" in one place and "Remove" in another for the same action)

**Responsiveness & adaptability**
- [ ] Layouts tested across breakpoints (mobile, tablet, desktop) — not just resized, but re-flowed sensibly
- [ ] RTL support verified if targeting Arabic or other RTL locales (this one's worth flagging given your Arabic portfolio work — vibe-coded layouts often break silently in RTL because AI defaults to LTR assumptions)
- [ ] Safe areas respected on mobile (notches, home indicators)

**Trust & clarity**
- [ ] Form validation happens inline, not only on submit
- [ ] Navigation is predictable (back button behaves as expected, breadcrumbs where needed)
- [ ] Onboarding/empty states guide first-time users rather than showing a blank screen
